# 升级、停用和回退

操作前保存原始 ecosystem/service 配置、Guard 配置、当前提交号及脱敏状态。使用运行目标应用的同一账户和进程管理器。应用名重复时，先通过 `pm2 jlist` 核对 ID、cwd、script 和 unique_id，避免操作其他项目。

## 自动更新

发布包安装可以由 Guard 自己更新：主人发送 `#guard更新`（`#guard强制更新` 重装最新版并允许跨主版本）、控制台总览页按钮或 CLI `update [--force]`。流程：

1. 读取最新 Release，下载本平台发布包与 `SHA256SUMS.txt`，校验摘要，解压到插件目录内的 `.update/staged`，核对包名、版本和入口文件。
2. 停止业务进程，把 `dist`、`native`、`package.json` 等发布文件逐项重命名替换，旧文件移到 `.update/previous`；Windows 的 `runtime/` 只补充缺少的 Node 目录，不动正在使用的副本。任何一步失败都会还原。
3. 启动新业务进程；未能上线则还原并重启旧版本，结果通知主人。
4. 冷启动宿主随后用新文件重新启动自己。launcher、PM2 与 systemd 托管时宿主保持旧代码运行，面板会标明“宿主需重启后完全生效”，请按各自方式重启。

更新不提供降级：最新发布低于当前版本时直接拒绝。Windows 上新版本在启动阶段就崩溃、旧进程又无法确认已清理时，宿主会熔断（文件已还原），重启宿主即可恢复。

Git 安装不会被替换，仅提示新版本。手动回退：停止后把 `.update/previous` 中的内容移回插件目录，再启动。

## 升级

1. 通过所属启动器停止目标应用，防止其自动拉起。
2. 确认 Guard 宿主、工作进程及其后代退出，系统沙箱权限和资源已回收。
3. 更新整个插件版本，再在插件目录执行 `npm ci --include=dev` 自动编译配套产物；不要逐文件覆盖仍在运行的模块。`dist` 不纳入 Git，不能省略安装步骤。
4. 核对目标版本的配置要求，然后重新启动宿主并检查 `status` 和受影响的业务功能。

回退采用相同步骤，并先确认配置字段与旧版本兼容。Guard 保留已有显式权限决定，不会因为默认值变化自动取消用户配置的 `deny`、`restart` 或沙箱选择。

PM2 daemon 可能缓存旧 Guard 模块，更新磁盘文件并不自动替换缓存。现有升级路径只迁移能够识别且处于可迁移状态的登记；未知形状、未完成回调或能力不符会拒绝。不能承诺任意旧版本之间的热升级，也不应为绕过缓存而重启同时托管其他应用的 daemon。没有适用迁移路径时，可先定向停用 Guard，以原入口运行 Yunzai。

## PM2 定向停用或卸载

1. 执行 `pm2 stop <目标 ID>`，确认目标进程和系统沙箱资源退出。
2. 执行 `pm2 delete <目标 ID>` 删除旧条目。自动接管后的条目可能指向 Guard launcher，仅修改原配置再 `restart` 不会解除登记。
3. 将 `plugins/yunzai-guard` 移到 **plugins 目录之外** 的备份位置。只在 plugins 内改名仍可能被核心加载。
4. 执行 `pm2 start <原 ecosystem 文件> --only <目标名称>`，按原 `app.js` 入口创建新条目。
5. 核对新条目的工作目录、入口和身份，确认业务启动，且其他应用保持预期状态，再执行 `pm2 save`。

`pm2 save` 保存整个当前清单，执行前应确认没有意外遗漏其他应用。此流程不需要 `pm2 kill`、`update` 或 `restart all`。daemon 内旧适配代码会保留至 daemon 自然退出，但旧登记不应匹配新应用身份。

重新启用时，停止并删除当前目标、确认资源退出、移回插件，再从原配置启动并保存清单。

## 普通 Node、screen/tmux 与 systemd

通过所属启动器停止服务并阻止本次自动拉起，等待进程和权限回收。移出插件后，将显式 launcher 或预加载配置恢复为原 `app.js`，再按原方式启动。systemd 的 `ExecStart` 不得继续指向已移除的 Guard 文件。

直接使用原 `app.js` 的普通启动无需修改入口。应保留原配置和业务数据，待确认回退正常后再决定是否删除 Guard 自身状态。

## 配置与数据保留

面板保存配置后按[字段范围](PERMISSIONS.md#配置生效)自动应用；手工修改 `settings.json` 或离线 CLI 配置后仍需完整重启宿主，CLI `restart` 只重建工作进程。解除熔断前先修正原因，再运行 `resume`，避免重复消耗恢复预算。

独立插件沙箱的文件及 Redis 授权使用原业务路径和键名。停用沙箱或卸载 Guard 不需要导出业务数据，也不应清理其他插件目录。旧测试版留下的 Guard 前缀 Redis 键不会自动迁移或删除；确需合并时应另行确认键名和冲突处理。

回收失败时保留恢复证据，先处理状态再启动下一代。强杀进程、删除控制文件或清空 Guard 数据目录不能代替确认系统权限已恢复。
